# Zenoh 1.10.1 routing declaration ordering

The session history gate orders an API subscriber's cached history and live
callbacks. It does not order declarations generated by the routing layer.
Zenoh 1.10.1 computes a batch under `TablesLock::ctrl_lock`, releases the lock,
and sends that caller's private vector. Another caller can compute and send a
withdrawal before the earlier vector sends its Current token declaration.
The receiver then removes the token and subsequently recreates it from the
old declaration. A fresh subscriber can inherit that incorrect routing state.

The fixed source is the published 1.10.1 crate at upstream commit
`1211779c3647f5a96713dade452c546a07823580`; archive and license identities are
unchanged. This is an AOS local patch, not an accepted upstream fix.
The [complete vendor manifest](zenoh-1.10.1-vendor-manifest.json) and
[replayable patch](patches/zenoh-1.10.1-liveliness-history.patch) cover both
the session history gate and the routing outbox. The hidden compile-time
patch marker is version 2. Its definition lives beside `RoutingDeclarations`
in `dispatcher/tables.rs`; `Session` re-exports that value. The marker detects
a missing routing core, while exact file hashes and complete patch replay
remain the check against partial or arbitrary source edits.

## Ordering contract

Every routing entity Declare/Undeclare and DeclareFinal for a destination
enters one FIFO in the same control-lock critical section that generates it.
Generation and enqueue are not separated by an unlock. A drain guard is
created before the control/table guards, so normal return and early `?` return
release every routing/resource lock before dispatch.

The guard registers a synchronous production batch in the outbox's per-thread
stack. Every enqueue records its destination in that batch; router-hat calls
through `TablesData::declarations` join the same stack. The guard is `!Send`
and never crosses an await. Before dispatch, it removes its batch from the
stack and may claim only that batch's touched destinations. An empty tree
worker/timeout batch cannot steal a local Session's unrelated pending lane.
Nested calls get their own touched set. Every idle nonempty lane therefore
has its generating producer responsible for draining it.

Each destination has at most one drainer. The queue mutex only protects
enqueue, pop and ownership bookkeeping; it is released before calling a
primitive or user callback. A busy lane accepts new items without waiting.
Its existing drainer delivers them after earlier queued items. Reentrant
callbacks therefore enqueue and return; they do not recursively deliver on
the same destination or take ownership from another thread. Another thread
can drain an independent destination while one callback remains blocked.

For a busy destination, a routing operation can return after committing its
state and enqueueing its declaration, before that declaration reaches its
callback. These operations do not promise synchronous callback completion.
There is no global order across destinations or across other protocol message
types.

This weakens the upstream per-caller **declaration before later data**
behavior. For example, while observer S's Declare callback is blocked,
`token.undeclare().wait()` may return after enqueueing S's Delete; the same
producer's subsequent `session.put(...).wait()` may deliver a Push to S before
that Delete. Upstream sent the producer's private declaration batch before
returning from undeclare. Applications must not use `.wait()` as a remote
declaration-delivery barrier or infer control/data ordering from this patch.

**Callback contract:** a native Zenoh callback must return without
synchronously waiting for a Declare-backed result on **any Session**. This
includes `liveliness().get(...).wait()` followed by blocking `recv`, waiting
for a matching change, and joining another thread that performs that wait.
The reply/Final can be queued behind the running callback, an outer callback
on another Session, or another thread's mutually waiting callback. A same-lane
blocking get returns only when its query timer emits Timeout. A callback may register an operation
and return, then let a separate application/executor turn await the result.
Recursive delivery is deliberately forbidden: an inner Delete followed by an
outer Put completing later would reintroduce the ordering defect.

There is an additional known consequence of violating this contract: a
Current-only liveliness get can time out before its queued Token reply
arrives. Zenoh 1.10.1 then inserts the late reply into `remote_tokens` after
removing the query. Without a matching Future interest the observer receives
no subsequent withdrawal for that key. A fresh `history(true)` watch can
therefore replay a stale Put even after the provider withdrew its token.
The two negative contract tests assert this history ghost explicitly. This
patch documents that unsupported usage; it does not repair late query replies.

The indexed lane and its active drainer both retain the destination `Arc`.
An empty check, owner release and index removal happen under the same mutex.
The destination cannot be deallocated and its address reused while its old
lane is still active. A touched production batch also retains its destinations
until it finishes; a close/removal cannot make a parked old batch select a new
destination at a reused address. Empty lanes retain no destination references.

Dispatch catches a callback or drain-diagnostic panic outside all locks, drains the batch's touched
lanes in FIFO order, releases ownership, then resumes the first panic on
ordinary callers. The active owner may dispatch another producer's items on
the same lane, so callback panic attribution follows the drainer, not the
producer that originally enqueued that item. The tree worker,
CurrentInterestCleanup, transport DeMux Declare/Interest/OAM handling, rejected
Interest handling, transport close and transport creation use the same drain
inside a background panic boundary. Nested Face batches inherit that boundary;
they log the restored panic and let the transport or worker continue. They do
not claim unrelated lanes. Push, Request, Response and ResponseFinal ingress
do not create an outbox batch or acquire its mutex merely to dispatch a message.
Their native data/query callbacks keep the upstream panic behavior, and API
calls made by those callbacks do not inherit transport declaration isolation.

A Drop guard still drains when the application thread is already unwinding,
including declarations generated by Subscriber/Token destructors. It uses
the isolated boundary to suppress a second callback panic and preserve the
original application panic. It never abandons an idle nonempty lane merely
because `thread::panicking()` is true. This dispatch happens after routing
locks have been released. If the producer itself panicked while mutating
routing state, the guard still dispatches declarations already enqueued before
that panic. This is intentional and differs from upstream discarding its
private batch on unwind. It does not undo the partial mutation: the routing
locks are poisoned and that router must not be reused.
An additional owner guard clears ownership on unexpected unwinding. This
does not roll back a routing-table mutation that itself panics, recover a
sample whose callback panicked, or make application callback state valid after
a panic.

Panic isolation requires Rust unwinding. The workspace has no `panic =
"abort"` profile override; the recorded release cfg is `panic="unwind"`.
A downstream build that overrides this to abort cannot use catch_unwind as a
recovery guarantee.

## Producer audit

| Producer | Enqueue and unlock boundary |
| --- | --- |
| `Face::send_interest` | Current/CurrentFuture replies and Final processing share the control critical section; drain after the method releases its locks. |
| `Face::send_declare` | Subscriber, Queryable, Token and Final arms use the same outbox instead of private vectors. |
| `Face::send_close` | Pending-interest Final and entity withdrawals enqueue under the same lock; retiring the closed destination discards its own useless pending queue; other destinations drain after unlock. |
| `CurrentInterestCleanup::execute` | Timeout/rejection Final is generated and enqueued before dropping the control lock. |
| `Gateway` session/transport creation | Face initialization uses the outbox; scope guards also cover early error returns. |
| `DeMux` OAM and rejected Interest | OAM-generated declarations and the rejection Final enqueue under the control lock and drain after unlock. |
| Router sourced entities | All six direct sends for Subscriber, Queryable and Token Declare/Undeclare now enqueue in the shared outbox. |
| Router tree worker | Takes control before the table write lock; drains only touched lanes after unlock and isolates callback panic. |

The full-net producer search has additional legitimate matches beyond the
queue's actual destination send. `hat/{client,peer,broker}` and
`hat/router/interests.rs` call the supplied `ctx.send_declare`/`SendDeclare`
callback (or an empty unsupported Final method); their dispatcher entrypoints
now supply enqueue. No `declares.push` private-vector collector remains in
`src/net`. `Namespace::send_declare` forwards API input to a Face, and its
EPrimitives implementation forwards already dequeued destination output.
`runtime/adminspace.rs` obtains `Gateway::new_session`'s `Arc<Face>` and sends
its two API-side declarations into `Face::send_declare`. These are not
unserialized destination-generation paths. The broader multiline method-call
search also includes DeMux-to-Face ingress, AdminSpace's receive-side
EPrimitives-to-Primitives adapter, and the `cfg(test)` harness under
`net/tests`; none generates an unqueued production destination declaration.
The exact rg output and callback inventory accompany the review evidence.

`Resource::decl_key` remains synchronous. It returns a full expression for
local sessions, so this path does not invoke a local subscriber callback.
For a network face it sends a key-expression compression mapping before
exposing that mapping to a dependent Interest, entity declaration or data
message. Delaying that mapping without also ordering those consumers would
introduce a new unresolved-prefix race. Local mapping IDs remain registered
until that face closes. Forwarded Interest and data paths retain their
upstream behavior. The contract is entity-declaration FIFO, not total wire
ordering across all protocol messages.

## Close and resource limits

For a surviving observer, a provider's queued Current declarations precede
the withdrawals generated by provider close. A provider close cannot let an
old Current declaration resurrect that provider's token afterward.

Observer close is not a flush guarantee. The existing
`WeakSession::close_inner` removes primitives, closes history gates and
clears callback/resource maps before invoking `Face::send_close`.
The `WeakSession::send_declare` arms check that the session is still open
before collecting new callbacks. A callback already collected or running may
finish. In the Face close path, the outbox removes pending items for that
closed destination. Idle lanes are removed immediately; an active lane keeps
only its in-flight owner until the callback returns. Removed payloads and
destination references are dropped after releasing routing and outbox locks.
The transport's `DeMux::closed` also runs after its connection has closed.
This patch does not add a new transport-close barrier.

The close regressions explicitly use public `session::init(DynamicRuntime)`:
`InitBuilder::wait` converts `DynamicRuntime` to `GenericRuntime` with
`static_runtime=None`, so closing one plugin Session invokes Face close and
leaves the shared Runtime and the other Session open. The tests assert that
property. `zenoh::open` instead owns a static Runtime and takes the existing
whole-runtime shutdown branch. The plugin tests do not establish that the
static-runtime branch invokes Face close for its local Session.

There is no lossy queue capacity or permanent token tombstone. Queue size
depends on the pending Current batch, entity/control traffic and how quickly
the destination's callback/transport drains. Once a callback returns and
producers quiesce, the FIFO drains and its lane is removed. A callback that
blocks forever, or sustained production faster than delivery, can retain an
unbounded backlog. The implementation does not claim bounded memory under
those conditions.

Pending counts and high-water marks exist in production. Enqueue and drain
observe lane backlog and current owner age; at 1,024 pending declarations or
one second of ownership, they emit a warning with lane/total pending and
high-water values, the concrete primitives kind, and the Mux face id/ZID when
available. The pointer remains a correlation key, not the only identity.
Warnings are limited to one per outbox per 30 seconds,
including across lane removal/recreation. This adds no background timer: a
permanently blocked callback with no further queue activity produces no new
periodic warning. A live target's sustained traffic may keep the caller
draining indefinitely; observing that duration is not a bounded-latency claim.

The deterministic pressure test uses four producers while one callback is
blocked. It records a high-water mark of 8,000 pending declarations, then
checks all 8,000 in generation order and verifies zero pending items and zero
indexed lanes. This finite test is not a proof of a bound for permanently
blocked callbacks.

## Regression gates

`crates/aos-zenoh/tests/routing_order.rs` creates two independent API sessions
sharing an upstream Runtime. It blocks the first public callback of a
two-token Current batch, then synchronously withdraws the other token before
releasing that callback. It uses no arbitrary sleep, routing test hook or
diagnostic production code. The history-only vendor failed the withdrawal
case in 0.01 seconds; the outbox must deliver the pending Put before Delete.
Additional cases close the provider during the blocked batch and close the
observer before permitting its in-flight callback to finish.
Before releasing the Current callback, the tests assert that the target
Delete has neither begun nor completed.

Two negative contract tests use an 80 ms get timeout. Both a same-thread
blocking get and a callback joining another thread's get receive Timeout;
the identical query succeeds after the callback returns, and the delayed
reply remains visible as a history ghost after provider withdrawal. These tests record
the unsupported usage instead of claiming it was made synchronous.

The network tests create a token, queryable and subscriber on router A before
connecting router B, so existing entities must propagate over the new route.
They start two real TCP router runtimes with distinct ZIDs,
exercise Subscriber/Queryable/Token Declare and Undeclare, get/DeclareFinal,
eight token churn rounds, and actual Push/query replies. They require
`handle_oam`, decoded linkstate and `Compute trees` trace evidence from the
router source. A separate TCP client test proves an allowed liveliness get
succeeds and an ACL-denied ingress Interest closes with zero replies before
its 30-second query timer, exercising DeMux's rejection Final.
The unwind tests catch an application panic that drops a live Token or a
regular Subscriber, then require the observer's Delete or publisher's unmatch
without issuing any later declaration, get or close. Another
TCP test panics in the first declaration callback and requires a later Put
and both Deletes on the same observer, proving that DeMux's inherited
background boundary keeps its declaration RX path alive. Removing parent
background inheritance makes that test fail after the first callback panic;
it cannot receive the subsequent token Put.

The shared-runtime initializer uses upstream's `internal` feature. The existing
ordinary dependency `zenoh-ext/unstable` already enables `zenoh/internal`,
including for the Python release dependency graph. This patch adds no feature
or dev dependency; both Cargo manifests and that ordinary feature graph remain
unchanged. It does not claim that `internal` is disabled in production.
Each Session case runs in a subprocess and verifies its exact test name and
`1 passed` summary, so a zero-test child cannot count as success.

`crates/aos-zenoh/tests/routing_outbox.rs` includes the exact vendored helper.
Its sixteen tests cover FIFO reentry, independent-lane progress, touched-lane
ownership across the unlock/drain gap, first-panic restoration, background
panic isolation, idle/busy destination retirement, production warning/rate
limits, owner age, concurrent enqueue/reentry/panic and the 8,000-item pressure
case. Three cases cover ordinary unwind, a second callback panic during
unwind, and inherited transport isolation followed by ordinary propagation.
The diagnostic-panic case also requires the already popped item and every
remaining destination to be visited before restoring the panic. These tests
run with ordinary workspace tests.

`scripts/test_zenoh_demux_scope.py` runs the vendored `cfg(test)` DeMux test:
128 Push messages must add zero declaration batches. Reinstating the R3
all-message scope makes the same counter assertion fail with 128 new batches.
The counter is absent from production builds. The helper uses an isolated copy
with the published crate's own locked dev-dependency graph; it omits only the
unrelated `link_weights` test module whose `zenoh_test` dev-dependency is absent
from the published crate. It verifies all routing-source bytes are unchanged
and never edits the production vendor to run this harness.

## AOS callback audit

The adapter's callback inventory has seven sites. None waits for a
Declare-backed result on any Session or invokes an application callback.

| Site | Work performed inside the callback |
| --- | --- |
| `graph.rs` watch | Parse a graph key; update the private map; release its mutex; enqueue a coalesced wakeup. |
| `graph.rs` snapshot | Parse the reply and enqueue an owned result. The receive loop runs after registration, outside the native callback. |
| `pubsub.rs` matching listener | Enqueue a wakeup. Its wait-for-match receiver is outside the callback. |
| `pubsub.rs` subscriber | Copy an owned sample, record bounded telemetry and enqueue/evict it. |
| `service.rs` queryable | Enqueue an owned Query; if one is evicted, send an error Response outside the queue lock. That `.reply_err(...).wait()` sends a protocol reply and does not await a Declare-backed result. |
| `service.rs` two reply sites | Record bounded telemetry, settle owned result state and enqueue the reply. |

`session.rs` installs no callback and records only close/resource bookkeeping.
The adapter crate docs and the graph callback document the hard callback
contract; core/SDK executors consume owned queues outside middleware callbacks.
The [fixed zenoh-ext callback audit](zenoh-ext-callback-audit.md) also covers
publisher detection, late-publisher history, cache replies and recovery.
Its internal get callbacks release their state locks before issuing Requests
and do not synchronously receive Declare-backed results. Ext delivery handlers
still run under its own state lock; the AOS handler remains queue-only.

```sh
cargo test -p aos-zenoh --locked --test routing_order --test routing_outbox
cargo test -p aos-zenoh --locked --test liveliness_history --test readiness --test transport
python3 scripts/check_zenoh_vendor.py --archive /path/to/zenoh-1.10.1.crate
python3 scripts/test_zenoh_demux_scope.py --output work/zenoh-demux-scope
```

Passing these regressions does not by itself prove native Linux/macOS/Windows
or packaged-wheel acceptance. Those results remain separate recorded gates.
